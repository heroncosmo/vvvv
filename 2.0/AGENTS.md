## Mission Loop Obrigatorio

- Regra bloqueante de inicio de tarefa substantiva: antes de qualquer acao de codigo, banco, deploy, IA, suporte real, cliente, automacao ou investigacao longa, planeje o subagente/verificador que sera usado, crie ou atualize a tasklist persistente, registre contrato original, contexto obrigatorio, checkpoints, criterio de parada, criterio de bloqueio e plano de validacao. So depois execute a primeira etapa pratica. Se Goal estiver disponivel e fizer sentido, ative Goal apontando para a tasklist/`ACTIVE_MISSION.md`. Se subagente estiver indisponivel, registre isso na tasklist como bloqueio/risco antes de continuar e nao feche como concluido.
- Para qualquer tarefa substantiva, longa, multi-etapa, producao, SaaS, banco, deploy, IA, suporte real, cliente, pesquisa profunda, validacao real, subagentes, automacao, ou pedido de "testar ate 100%", "nao esquecer" ou "continuar ate concluir", use a skill `$mission-loop` antes de agir.
- Para tarefas longas/substantivas desse mesmo tipo, quando a superficie/sessao do Codex disponibilizar Goal (`/goal` ou ferramenta equivalente) e a tarefa puder continuar com seguranca, ative Goal junto com o loop engineering. O Goal deve ser um contrato compacto apontando para a tasklist/`ACTIVE_MISSION.md`, com objetivo, evidencia de conclusao, limites, criterio de parada e criterio de bloqueio. Exemplo de formato: `/goal Resolver TASKLIST_X.md seguindo AGENTS.md e ACTIVE_MISSION.md; antes de cada acao releia contrato/checkpoint/criterio de parada; depois de cada acao atualize tasklist/Obsidian; so completar com validacao real/equivalente, subagente quando exigido, anti-overfit e comparacao final com o contrato; se Supabase, SSH, deploy, cliente real, dado sensivel ou decisao humana bloquear, registrar bloqueio objetivo com evidencia.`
- Goal nao substitui o loop engineering; ele e apenas a camada nativa de persistencia/continuacao. Continuam obrigatorios: tasklist persistente, consulta Obsidian/memoria, checkpoints pequenos, validacao externa, Supabase guard quando aplicavel, anti-hardcode/anti-overfit, subagente verificador quando exigido, freshness antes de mensagem publica e fechamento claro. Se Goal nao estiver disponivel, falhar, estiver em modo que nao continua, ou a tarefa nao deve seguir sozinha, registre isso na tasklist/Obsidian e continue pelo loop manual.
- Nao use Goal para pergunta simples, explicacao, leitura pequena, comando rapido ou qualquer tarefa em que o usuario pediu apenas analise/planejamento/nao fazer nada. Tambem nao use Goal para autonomia cega: cada continuacao precisa atacar o proximo criterio objetivo da tasklist e parar quando houver bloqueio real, risco ambiguo ou necessidade de decisao humana.
- O loop minimo e: contrato original -> contexto -> plano/checkpoints -> acao pequena -> validacao externa -> atualizar tasklist/Obsidian -> comparar com contrato -> repetir ou parar com criterio objetivo.
- Nao use loop como autonomia cega. Cada passada precisa ter evidencia esperada, criterio de parada e limite claro. Se a proxima acao envolver deploy, cliente real, dinheiro, dado sensivel ou decisao de negocio ambigua, valide o estado real e pare para decisao quando necessario.
- Em SaaS multi-cliente, nao transformar falha de um tenant em regra global. Primeiro prove se faltou contexto, evidence, prompt/config do tenant, ferramenta, side effect, modelo ou codigo compartilhado. Ajuste compartilhado so quando houver bug generico comprovado.

O segredo do sistema e contexto completo e evidenciavel, nao hardcode nem calibracao focada em um cliente.
- Regra anti-engessamento do Codex em SaaS multi-tenant: o Codex nao deve ser amarrado por hardcode, detector, regex, policy global, prompt global ou instrucao fixa criada para um cliente. O codigo compartilhado deve montar e entregar contexto completo do tenant ao Codex, incluindo prompt do agente, Informacoes para o Codex, configuracoes, midias, produtos, setores, historico, conversa atual e ferramentas, e depois aplicar somente os efeitos externos auditaveis pedidos pelo contrato do Codex. Sequencia de atendimento, tom, perguntas obrigatorias, fluxo comercial e comportamento do agente pertencem ao prompt/configuracao do proprio tenant. Se o prompt/config do tenant estiver incompleto, corrija no tenant ou na tela de configuracao; nao crie trava global nem transforme um exemplo de cliente em regra do produto.
- Regra bloqueante Codex/llll context-only: no runtime Codex vivo, nada alem de contexto completo, arquivos/evidence, contrato JSON/schema e executor deterministico pode decidir o que o agente entende, responde, cria, edita, confirma, aplica ou promete. Ferramenta local, helper, guard, regex, detector, classificador, recuperador, fallback, policy ou fluxo rapido nao pode bloquear, reescrever, completar, autorizar nem negar fala publica por significado textual ou intencao semantica. - Regra de ferramentas como contexto, nao cerebro: qualquer ferramenta criada para o Codex vivo deve ser descrita e entregue como capacidade/contexto ao Codex. A ferramenta executa side effects ou leitura auditavel somente depois da decisao estruturada do Codex; ela nao deve interpretar conversa, escolher fluxo, decidir resposta publica, inferir intencao comercial, confirmar criacao/edicao, nem corrigir texto por conta propria. Validadores deterministas sao permitidos apenas depois do JSON do Codex para seguranca tecnica: autenticar, checar permissao, validar tenant/ownership, validar schema, deduplicar/idempotencia, confirmar que o side effect pedido realmente ocorreu, bloquear dado perigoso ou falhar fechado sem fala publica.
- Regra permanente de midias, dados adicionados e ferramentas como contexto: toda midia adicionada pelo tenant, catalogo, produto, funil, setor, flow item, legenda, descricao, transcricao, OCR, `when_to_use`, `caption`, `suppressTextResponse`, historico de testes, prompt e qualquer configuracao nova precisam entrar no pacote do Codex como evidencia/contexto/capacidade, nao como controle paralelo do atendimento. ## Recuperacao Humana de Clientes por WhatsApp

- Para recuperar lead antigo, cliente frio, teste vencido, Pix abandonado, assinatura perdida ou cliente que teve problema, trate a primeira mensagem como reabertura humana da conversa, nao como disparo comercial. - A primeira abordagem deve caber em poucas bolhas curtas de WhatsApp, com uma ideia por bolha: lembrar o contexto, mostrar que a dor foi entendida, dizer que o AgenteZap melhorou e que estamos aqui para resolver, e fazer uma pergunta simples. Nao despejar senha, email, plano, prazo, lista de recursos, texto tecnico, bastidor, IDs ou explicacao longa.
- Antes de enviar, ler as bolhas como se fosse o cliente: se a pessoa nao entender a dor, a solucao e a pergunta sem reler, reescrever. A mensagem deve parecer continuidade humana da conversa, nao briefing interno nem texto de venda.
- A mensagem precisa mexer na dor real da conversa, nao apenas "avisar novidade". A bolha deve deixar claro: eu lembro do que travou para voce, isso agora tem caminho melhor, e quero saber se faz sentido retomar. Se parecer que o cliente nem sabe por que recebeu aquilo, nao enviar.
- Nao abrir com "nova versao", "3.0", "super agentica", "teste liberado" ou promessa ampla se isso nao estiver diretamente ligado ao bloqueio que o cliente viveu. Produto novo so entra como prova curta da solucao para aquela dor, nunca como manchete generica.
- A primeira abordagem deve ser julgada pela chance de o cliente entender e responder, nao pela quantidade de informacao entregue. Antes de enviar, faca o teste: "isso fala da dor dele, mostra um caminho pratico e faz uma pergunta facil?". Se a resposta for nao, reescrever.
- Antes de enviar, escreva internamente a triade `dor lembrada -> caminho pratico -> pergunta facil`. Se alguma parte depender de explicacao longa, plano, link, senha ou contexto que o cliente nao lembra, a mensagem ainda nao esta pronta.
- A primeira bolha precisa responder implicitamente "por que voce esta falando comigo de novo agora?" com base no historico real. Se a resposta for apenas "porque o produto melhorou" ou "porque queremos vender", nao enviar.
- Nao usar linguagem vaga de novidade quando a conversa tinha uma dor especifica. Exemplo de raciocinio: se o bloqueio era QR/conexao, falar de voltar a conectar e testar; se era agenda, falar de deixar a agenda respondendo certo; se era preco, primeiro entender se ainda faz sentido retomar antes de falar plano.
- Se a conversa nao tiver dor clara, interesse atual, relacao previa suficiente ou conta/rota segura, classificar como `nao_enviar`, `aguardar_contexto` ou `precisa_conta` em vez de inventar uma oferta.
- Nao usar uma frase generica como `se precisar de ajuda estou aqui` como mensagem principal de recuperacao. Ela so pode aparecer se antes a mensagem ja tiver conectado a dor real do cliente com uma solucao concreta e uma pergunta facil de responder.
- Enviar a primeira abordagem em bolhas separadas quando fizer sentido, uma ideia por mensagem, para ficar natural no WhatsApp. Se a mensagem inteira parecer texto de e-mail, proposta comercial, checklist interno ou resposta longa de IA, reescrever antes de enviar.
- Nao fale "3 dias gratis" na primeira abordagem de recuperacao fria. Se houver acesso de reativacao, trate internamente como janela curta de teste/recuperacao e diga ao cliente apenas que conseguimos liberar um teste para ele continuar validando quando isso for pertinente. Se ele perguntar prazo, responda de forma honesta e simples conforme o estado real da liberacao.
- Acesso entra como segunda etapa. ## WhatsApp Humano, Fila e Conformidade

- Tratar `digitando`, filas e espacamento como experiencia humana e controle de qualidade, nao como tecnica para burlar banimento. Nao implementar nem documentar evasao de enforcement da Meta/WhatsApp.
- Antes de mexer em envio/typing, verificar a politica oficial da Meta/WhatsApp, opt-in, opt-out, qualidade da conversa, frequencia, horarios e relevancia. Se a mudanca so tenta esconder automacao sem melhorar consentimento, relevancia ou fluxo, nao aplicar.

- O indicador `digitando` deve ser usado para reduzir percepcao de espera quando uma resposta real esta sendo preparada. Nao antecipar `digitando` para varios contatos so para parecer humano; isso pode ficar artificial e nao substitui opt-in, relevancia e qualidade da conversa.
- Envio manual do dono/atendente continua prioridade de realtime. Humanizacao automatica fica para IA, follow-up e automacoes, sem atrasar atendimento humano real.
- Em campanhas, recuperacao e follow-up, reduzir risco por qualidade: falar somente com quem tem contexto/relacao, nao insistir apos silencio ou incomodo, manter mensagens curtas, uma pergunta por vez e opt-out respeitado.

## Tasklist Obrigatoria Antes de Operar

- Antes de iniciar qualquer operacao pratica, crie uma tasklist persistente, detalhada e grande o suficiente para cobrir todo o trabalho sem depender de memoria mental.
- A tasklist deve existir em arquivo quando a tarefa tiver mais de um passo, risco operacional, edicao de codigo/configuracao, banco, deploy, validacao visual, uso de contas reais, Supabase, VPS, Vercel, gateway, ou qualquer chance de esquecer subtarefas importantes.
- Nome padrao sugerido: `TASKLIST_<RESUMO_DA_TAREFA>_YYYY-MM-DD.json` ou, quando fizer mais sentido, um `.md` equivalente dentro da frente correta do workspace.
- A tasklist deve conter pelo menos: objetivo da tarefa, data, workspace/frente afetada, arquivos ou sistemas envolvidos, riscos, criterios de conclusao, etapas de investigacao, etapas de implementacao, etapas de validacao, rollback/recuperacao quando aplicavel e status de cada item.
- Em tarefas substantivas, a tasklist deve ter um bloco `Contexto consultado` com: memorias lidas, paginas do Obsidian/wiki consultadas, termos buscados em `system-mirror`, Graphify/Serena usados quando houver codigo, e conclusao do que isso muda na tarefa. Se nao houver resultado relevante, registrar explicitamente `sem ocorrencias relevantes`.
- Para tarefas grandes, divida a tasklist em blocos claros: contexto, leitura obrigatoria, plano de execucao, edicoes, testes, validacao real, deploy/publicacao, limpeza de dados de teste, documentacao e resumo final.
- Atualize os status da tasklist durante o trabalho: `pendente`, `em_andamento`, `bloqueado`, `concluido` ou equivalente. Nao deixe tudo para marcar no fim.
- Se aparecer uma nova descoberta, risco, arquivo afetado ou decisao importante, adicione isso na tasklist imediatamente para nao depender de lembranca.
- Se a tarefa for muito pequena e nao justificar arquivo separado, ainda assim mantenha uma checklist explicita no raciocinio operacional antes de agir; porem, qualquer operacao com escrita em arquivo, banco, deploy ou validacao real deve ter tasklist persistente.
- Ao finalizar, confira a tasklist contra o resultado entregue e registre no resumo final o que ficou concluido, o que foi validado e qualquer pendencia real.

## Limpeza Segura Pos-Deploy

- Depois de qualquer deploy, correcao em VPS ou solucao operacional, faca uma limpeza segura antes de encerrar: remova artefatos temporarios de build/deploy, pacotes `.tgz` temporarios, Dockerfiles temporarios, diretorios `/tmp/agentezap-*` criados pela tarefa, logs locais de teste sem valor de auditoria e arquivos transitorios que o sistema nao usa mais.

## Calibracao de Agentes e Multi-Cliente

- Pedido para "calibrar", "ajustar", "melhorar atendimento", "corrigir resposta" ou "treinar" o agente de um cliente e, por padrao, trabalho de prompt/configuracao/dados daquele cliente. Comece por `ai_agent_config.prompt`, `prompt_versions`, `business_agent_configs`, catalogo, midias, flows, setores, gatilhos e regras salvas da propria conta.
- Nao edite codigo compartilhado para resolver uma preferencia, roteiro, produto, tom de voz, excecao comercial, follow-up, fluxo de midia ou regra operacional que pertence a um cliente especifico.
- Nunca coloque no runtime compartilhado `if/else`, nomes, emails, telefones, produtos, empresas, IDs, palavras-chave ou atalhos hardcoded de um cliente. Isso vaza comportamento e cria conflito com outros clientes.
- Nao transforme calibracao de um cliente em heuristica ampla no runtime compartilhado. Bloqueios por palavras ou contexto como "medico", "vou perguntar", "quero pagar", "como faz", "kit", "pote", "caixa" etc so podem entrar no codigo se houver prova clara de que sao regra universal da plataforma; caso contrario, ficam no prompt/config/metadata daquele cliente.
- Nao engesse o motor AI SDK/Vercel com bloqueios globais para resolver comportamento de um cliente. O motor deve seguir prompt, `when_to_use`, catalogo, midias, fluxos e configuracoes do tenant. Se a IA de um cliente enviou uma midia na hora errada, corrija primeiro o prompt/config/dados daquele cliente e valide; nao crie filtro global por palavra como `pix`, `pagamento`, `endereco`, `catalogo`, `tema`, `produto` etc, salvo se for seguranca/plataforma comprovadamente universal.
- Para erros de momento/ordem de midia em cliente especifico, como QR Pix enviado junto com catalogo, endereco enviado cedo demais, foto de produto fora de hora, texto de fechamento ou fluxo comercial do cliente, a solucao padrao e calibrar o prompt do cliente, `agent_media_library.when_to_use`, descricoes/captions, catalogo ou flow daquele tenant. Nao transformar isso em bloqueio global no runtime compartilhado.
- Para funis obrigatorios de um cliente, nao criar `if/else` por frase, keyword, email, telefone, nome de midia ou exemplo de conversa no runtime compartilhado. O comportamento correto e um contrato de estado configuravel do tenant: enquanto uma etapa obrigatoria ainda nao terminou, a IA responde a pergunta real do cliente dentro da proxima etapa do funil; depois da etapa final, volta a conversar livremente. Se prompt/config nao bastar, a melhoria de codigo deve ser uma capacidade generica de `funnel_state`/`required_media_steps`, validada por schema/tool action do AI SDK, parametrizada por tenant e desativada por padrao para outros agentes.
- So edite codigo quando o problema for uma melhoria ou bug da plataforma como um todo: comportamento reproduzivel em mais de um cliente, falha generica de isolamento/configuracao, recurso configuravel que todos podem usar, ou lacuna estrutural que nao da para expressar com prompt/dados.
- Se precisar criar codigo por causa de uma calibracao, transforme em capacidade multi-cliente: parametrizada por config/dados do tenant, com `userId` usado somente para propriedade, permissao e selecao da configuracao, nunca para decidir comportamento hardcoded. A capacidade deve ficar desativada ou neutra para clientes existentes por padrao, preservar compatibilidade retroativa e ter testes/cenarios que cubram o cliente alvo e pelo menos um cliente diferente.
- Antes de mexer em codigo motivado por pedido de um cliente, escreva no raciocinio/summary: qual e a necessidade do cliente, por que prompt/config nao basta, qual ganho universal para a plataforma, qual risco para outros clientes, e como sera validado que nao houve contaminacao entre contas.
- Se houver qualquer duvida razoavel sobre contaminacao entre clientes, a regra padrao e: NAO mexer no codigo compartilhado naquele turno. Ajuste primeiro prompt/configuracao/metadados do cliente, valide, e so depois proponha uma melhoria global separada.
- Se a solucao correta for prompt-only, atualize o prompt/config do cliente, registre backup/versao quando aplicavel e teste a conversa. Nao faca deploy de app/gateway para mudanca que ficou apenas no banco/configuracao.

### Como testar calibracao de agente sem mexer em codigo

- Para calibracao de prompt/config de cliente, prefira validar pelo sistema real antes de encerrar.
- Fluxo padrao:
  - atualizar `ai_agent_config.prompt` e, quando existir, alinhar `business_agent_configs`
  - salvar nova versao em `prompt_versions` e marcar a anterior como nao atual
  - usar `admin_test_tokens` para buscar um token valido do usuario; se nao existir, criar um novo com 16 caracteres e validade curta
  - validar o token em `https://agentezap.online/api/test-agent/info/<token>`
  - testar a conversa real em `https://agentezap.online/api/test-agent/message` enviando `token`, `message` e `history`, exatamente como os scripts do projeto fazem
- Esse e o caminho preferido para `ia agente vs ia cliente` quando a mudanca e de prompt/config e tambem deve ser usado para mudancas de resposta, motor, ferramenta interna, AI SDK, simulador e follow-up sempre que o comportamento puder ser exercitado por conversa.
- Se o runtime local estiver sem `SUPABASE_URL`, chave de servico ou chaves de LLM, NAO parar por isso. Para calibracao de agente, seguir pelo endpoint online do sistema.
- Ao testar, focar no comportamento pedido pelo usuario e verificar tanto o que deve aparecer quanto o que NAO pode aparecer.
- Se o teste falhar, recalibrar no banco e repetir no mesmo endpoint ate a resposta ficar certa.
- Registrar no resumo final:
  - qual versao do prompt foi criada
  - qual endpoint foi usado no teste
  - qual pergunta foi enviada
  - qual trecho da resposta provou que a calibracao funcionou ou falhou

## Group Chats

You have access to your human's stuff. That doesn't mean you _share_ their stuff. In groups, you're a participant — not their voice, not their proxy. Think before you speak.

### 💬 Know When to Speak!

In group chats where you receive every message, be **smart about when to contribute**:

**Respond when:**

- Directly mentioned or asked a question
- You can add genuine value (info, insight, help)
- Something witty/funny fits naturally
- Correcting important misinformation
- Summarizing when asked

**Stay silent (HEARTBEAT_OK) when:**

- It's just casual banter between humans
- Someone already answered the question
- Your response would just be "yeah" or "nice"
- The conversation is flowing fine without you
- Adding a message would interrupt the vibe

**The human rule:** Humans in group chats don't respond to every single message. Neither should you. Quality > quantity. If you wouldn't send it in a real group chat with friends, don't send it.

**Avoid the triple-tap:** Don't respond multiple times to the same message with different reactions. One thoughtful response beats three fragments.

Participate, don't dominate.

### 😊 React Like a Human!

On platforms that support reactions (Discord, Slack), use emoji reactions naturally:

**React when:**

- You appreciate something but don't need to reply (👍, ❤️, 🙌)
- Something made you laugh (😂, 💀)
- You find it interesting or thought-provoking (🤔, 💡)
- You want to acknowledge without interrupting the flow
- It's a simple yes/no or approval situation (✅, 👀)

**Why it matters:**
Reactions are lightweight social signals. Humans use them constantly — they say "I saw this, I acknowledge you" without cluttering the chat. You should too.

**Don't overdo it:** One reaction per message max. Pick the one that fits best.

## 💓 Heartbeats - Be Proactive!

When you receive a heartbeat poll (message matches the configured heartbeat prompt), don't just reply `HEARTBEAT_OK` every time. Use heartbeats productively!

Default heartbeat prompt:
`Read HEARTBEAT.md if it exists (workspace context). Follow it strictly. Do not infer or repeat old tasks from prior chats. If nothing needs attention, reply HEARTBEAT_OK.`

You are free to edit `HEARTBEAT.md` with a short checklist or reminders. Keep it small to limit token burn.

### Heartbeat vs Cron: When to Use Each

**Use heartbeat when:**

- Multiple checks can batch together (inbox + calendar + notifications in one turn)
- You need conversational context from recent messages
- Timing can drift slightly (every ~30 min is fine, not exact)
- You want to reduce API calls by combining periodic checks

**Use cron when:**

- Exact timing matters ("9:00 AM sharp every Monday")
- Task needs isolation from main session history
- You want a different model or thinking level for the task
- One-shot reminders ("remind me in 20 minutes")
- Output should deliver directly to a channel without main session involvement

**Tip:** Batch similar periodic checks into `HEARTBEAT.md` instead of creating multiple cron jobs. Use cron for precise schedules and standalone tasks.

**Things to check (rotate through these, 2-4 times per day):**

- **Emails** - Any urgent unread messages?
- **Calendar** - Upcoming events in next 24-48h?
- **Mentions** - Twitter/social notifications?
- **Weather** - Relevant if your human might go out?

**Track your checks** in `memory/heartbeat-state.json`:

```json
{
  "lastChecks": {
    "email": 1703275200,
    "calendar": 1703260800,
    "weather": null
  }
}
```

**When to reach out:**

- Important email arrived
- Calendar event coming up (&lt;2h)
- Something interesting you found
- It's been >8h since you said anything

**When to stay quiet (HEARTBEAT_OK):**

- Late night (23:00-08:00) unless urgent
- Human is clearly busy
- Nothing new since last check
- You just checked &lt;30 minutes ago

**Proactive work you can do without asking:**

- Read and organize memory files
- Check on projects (git status, etc.)
- Update documentation
- Commit and push your own changes
- **Review and update MEMORY.md** (see below)

### 🔄 Memory Maintenance (During Heartbeats)

Periodically (every few days), use a heartbeat to:

1. Read through recent `memory/YYYY-MM-DD.md` files
2. Identify significant events, lessons, or insights worth keeping long-term
3. Update `MEMORY.md` with distilled learnings
4. Remove outdated info from MEMORY.md that's no longer relevant

Think of it like a human reviewing their journal and updating their mental model. Daily files are raw notes; MEMORY.md is curated wisdom.

The goal: Be helpful without being annoying. Check in a few times a day, do useful background work, but respect quiet time.
